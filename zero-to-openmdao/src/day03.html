3.1Why functions?

You've already used functions others wrote: print, len, math.sqrt. Today you write your own. A function is a named, reusable recipe: you give it inputs, it does its work, and it hands back an answer. Functions let you:

  • write a calculation once and use it many times
  • give a piece of logic a clear name, like density(h)
  • test one piece at a time

OpenMDAO components, Dymos ODEs and SciPy optimizers are all built from functions, so this is a key day.

3.2Defining and calling a function

New file d03_function.py:

{{code:d03_function.py}} {{out:d03_function.py}}
def density(h):
def means "define a function". density is the name you choose. h inside the brackets is a parameter, a placeholder name for the input the function will receive. The line ends with a colon.
"""Return air density…"""
A docstring: a description in triple quotes on the first line inside the function. It's optional but good practice. VS Code shows it when you hover over the function name.
rho = 1.225 * math.exp(-h / 8500.0)
The function's work, indented. h holds whatever value was passed in.
return rho
return sends the answer back to whoever called the function, and ends the function right there.
print(density(0))
Calling the function. Python sets h = 0, runs the indented lines, and density(0) is replaced by the returned value, 1.225, which is printed.
rho_cruise = density(10000)
You can store the returned value in a variable and use it later.

Defining a function does not run it. The lines under def only run when the function is called. A function must be defined (higher up in the file) before you call it.

Common confusion: return vs print

print shows a value on the screen, and that's all. return hands the value back so your program can keep calculating with it. A function that prints but doesn't return gives back None, Python's word for "nothing". If you get TypeError: unsupported operand type(s) … 'NoneType', a function you called probably forgot to return.

3.3Several parameters, default values and keywords

New file d03_params.py:

{{code:d03_params.py}} {{out:d03_params.py}}
def dynamic_pressure(rho, v):
Two parameters, separated by a comma. When you call dynamic_pressure(0.4135, 250.0), values are matched by position: the first goes to rho, the second to v.
def lift(q, S, CL=0.5):
CL=0.5 is a default value. If the caller doesn't give a CL, it's 0.5. Parameters with defaults must come after the ones without.
lift(q, 10.0)
Uses the default CL = 0.5.
lift(q, S=10.0, CL=0.8)
Keyword arguments: you name which parameter gets which value. This is clearer, and the order no longer matters (see the last line). OpenMDAO uses keyword arguments everywhere, for example units='m'.

3.4Returning two answers: tuples and unpacking

New file d03_return_two.py:

{{code:d03_return_two.py}} {{out:d03_return_two.py}}
return rho, T
Returns both values bundled together in a tuple. A tuple is like a list but is written with round brackets and can't be changed after it's made.
rho, T = atmosphere(5000)
Unpacking: the two values in the tuple are stored in two names, in order. The counts must match.
result[0]
You can also index a tuple like a list.

You'll often see unpacking used to set several variables in one line: x, y = 0.0, 0.0.

The if/else inside the function gives a slightly more realistic temperature: it falls by 6.5 K per km up to 11 km, then stays at 216.65 K.

Variables created inside a function (energy here) exist only while the function runs. Outside, Python has never heard of them. This is called scope, and it's a good thing: functions can't accidentally mess up each other's variables. The rule is information goes in through parameters and comes out through return.

3.6Dictionaries: values with labels

A list finds things by position number. A dictionary finds things by a key, a label you choose, like looking up a word in a real dictionary. New file d03_dict.py:

{{code:d03_dict.py}} {{out:d03_dict.py}}
vehicle = { "name": "Glider-1", "mass": 500.0, … }
Curly braces make a dictionary. Each entry is key: value, and entries are separated by commas. You may spread it over several lines for readability.
vehicle["mass"]
Look up the value stored under the key "mass". Note the square brackets.
vehicle["k"] = 0.1
Storing under a new key adds an entry. Storing under an existing key replaces its value.
"S" in vehicle
True if that key exists.
for key, value in vehicle.items():
.items() gives (key, value) pairs, which the loop unpacks into two names.

Why this matters for OpenMDAO

In OpenMDAO you'll write inputs['h'] and outputs['q'] = …. Those work exactly like dictionaries: look up or store a value by its name.

Common error: KeyError

Asking for a key that doesn't exist, like vehicle["Mass"] with a capital M, gives KeyError: 'Mass'.

3.7Your first optimizer: try everything, keep the best

Now combine everything. We wrap the Day 2 projectile simulation in a function, then try every launch angle and keep the one that flies farthest. That's an optimization: the angle is the design variable, the range is the objective, and the loop is the (very simple) search. New file d03_brute_force.py:

{{code:d03_brute_force.py}} {{out:d03_brute_force.py}}
def projectile_range(angle_deg, v0=100.0, k=0.0):
The whole simulation becomes one reusable function. Speed and drag have defaults; the angle must be given.
x, y = 0.0, 0.0
Unpacking, used to set two variables in one line.
return x
When the loop ends (the shot hit the ground), hand back how far it went.
best_angle = 0 and best_range = 0.0
The "best so far". It starts at nothing.
for angle in range(1, 90):
Try 1°, 2°, …, 89°.
if r > best_range:
If this angle beat the best so far, remember it. This "keep the best so far" pattern is worth memorizing.

Without drag the best angle is the textbook 45°. With drag it's 41°: drag punishes the long, high flight of steep shots. Trying every option works here because there's only one design variable. With ten design variables you'd need billions of tries, which is why real optimizers (Days 7 and 10) use slopes to search more cleverly.
