7.2Equations of motion with solve_ivp

On Day 2 you wrote a simulation by hand with Euler steps. That method needs tiny steps to be accurate. SciPy's solve_ivp does the same job properly: it picks its own step sizes and keeps errors small. ("IVP" means initial value problem: you know the starting state and want to know what happens next.)

You describe the physics as an ODE (ordinary differential equation). An ODE is a function that, given the time and the current state, returns the rates (how fast each part of the state changes). That's exactly the structure of your HGV compute and of every Dymos ODE. New file d07_solve_ivp.py:

{{code:d07_solve_ivp.py}} {{out:d07_solve_ivp.py}} {{img:projectile.png|What d07_solve_ivp.py shows}}
from scipy.integrate import solve_ivp
Imports the solver function from SciPy's integrate module.
def rates(t, state):
Your ODE. solve_ivp requires exactly these two parameters, in this order: the time, then the state (a list or array of numbers).
x, y, vx, vy = state
Unpack the state into readable names. The order is your choice, but you must keep it the same everywhere.
return [vx, vy, -k*speed*vx, -g - k*speed*vy]
The rates, in the same order as the state: dx/dt = vx, dy/dt = vy, then the two accelerations.
def hit_ground(t, state): return state[1]
An event function. solve_ivp watches its value and notices when it crosses zero, here when the height becomes 0.
hit_ground.terminal = True
Functions are objects too, so you can attach settings to them. terminal = True means "stop the simulation when this event happens".
hit_ground.direction = -1
Only count crossings going downward (positive to negative). Otherwise the start at height 0 could count.
solve_ivp(rates, (0, 100), start, events=hit_ground, max_step=0.05)
The ODE function, the time span (0 to 100 s at most), the starting state, the event, and a maximum step so the plotted curve is smooth.
sol.t and sol.y
sol.t is the array of times. sol.y is a 2D array: row 0 is x at every time, row 1 is y, and so on, in your state order.
x[-1]
The last x, which is where it landed.

596.1 m is exactly what your hand-written Euler loop found in Day 2's exercise 4. Two independent methods agreeing is a good sign.

7.3Optimization vocabulary

Every optimization problem has the same parts. OpenMDAO and Dymos use exactly these words:

WordMeaningCannonball example
Design variablewhat the optimizer is allowed to changelaunch angle
Objectivethe single number to make as small (or large) as possiblerange (make it large)
Boundsthe allowed range of each design variable1° to 89°
Constrainta condition on some result that must holde.g. peak height ≤ 150 m

Optimizers minimize by convention. To maximize something, minimize its negative: the largest range is the smallest "minus range". You'll see this trick everywhere.

7.4One design variable: minimize_scalar

New file d07_minimize_scalar.py:

{{code:d07_minimize_scalar.py}} {{out:d07_minimize_scalar.py}}
def flight_range(angle_deg):
Wraps a whole simulation: angle in, range out. To the optimizer it's just a function.
rtol=1e-8, atol=1e-8
Accuracy settings for solve_ivp: smaller means more accurate. Optimizers need smooth, accurate answers, because a jumpy function confuses them.
sol.y[0, -1]
Row 0 (x), last column (the landing point).
def objective(angle_deg): return -flight_range(angle_deg)
The minus sign turns "maximize range" into "minimize". This is the trick from 7.3.
minimize_scalar(objective, bounds=(1, 89), method="bounded")
Finds the angle between 1° and 89° that makes objective smallest.
result.success, result.x, result.fun
Whether it worked, the best design variable, and the objective value there. We print -result.fun to turn it back into a positive range.

40.92° matches Day 3's brute-force 41°, but the optimizer used about 10 simulations instead of 89, and gives a precise answer instead of a whole degree.

7.5Several design variables and a constraint: minimize

The classic test function used in OpenMDAO's own tutorials is f(x, y) = (x−3)² + xy + (y+4)² − 3. New file d07_minimize.py:

{{code:d07_minimize.py}} {{out:d07_minimize.py}}
def f(xy):
With several design variables, SciPy passes them together in one array. x, y = xy unpacks them.
x0=[3.0, -4.0]
The starting guess. Optimizers walk downhill from here.
method="SLSQP"
A popular gradient-based optimizer that handles constraints. OpenMDAO will use the same one.
con = {"type": "ineq", "fun": x_plus_y}
A constraint written as a dictionary. "ineq" (inequality) means SciPy keeps x_plus_y(xy) ≥ 0.

Unconstrained, the best point is x = 6.67, y = −7.33, f = −27.33. When x + y must be ≥ 0, the best allowed point is x = 7, y = −7, f = −27. On Days 8 and 10 you'll solve exactly this problem in OpenMDAO and should get identical numbers.
