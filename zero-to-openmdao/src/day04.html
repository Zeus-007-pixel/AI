4.1Your own module: a file of tools

As programs grow, one file gets messy. Any .py file can be used as a module: another file can import it and use its functions. Make atmos.py (no d04_ prefix, because other files will import it by this name):

{{code:atmos.py}} {{out:atmos.py|label=Output when you run atmos.py itself}}
RHO0 = 1.225
A fixed value used by the functions. By convention, names in CAPITALS mean "a constant: don't change this".
if h < 0: raise ValueError(...)
Stops the program with a clear message if someone asks for a negative altitude. Explained in 4.3.
if __name__ == "__main__":
Two underscores on each side. In plain words: "run the block below only when this file is run directly, and skip it when another file imports it". It's the place for quick tests of the module.

Now make d04_main.py in the same folder:

{{code:d04_main.py}} {{out:d04_main.py}}
import atmos
Python looks for atmos.py in the same folder and loads it. Notice the test block did not run this time.
atmos.density(10000)
Use a function from the module: module.function.
from atmos import temperature
Pulls one name straight in, so you can write temperature(…) without the atmos. prefix.

Why 223.14999999999998?

Computers store decimals in binary, so some values like 223.15 can't be stored exactly and tiny rounding errors appear. This is normal in every language. Use f-strings ({T:.2f}) when you display numbers.

4.2Libraries are just other people's modules

NumPy, SciPy and OpenMDAO are big collections of modules that pip installed for you on Day 1. You import them the same way. Often you give them a short nickname with as:

import numpy as np # now write np.sin instead of numpy.sin import openmdao.api as om # the OpenMDAO tools you need live in openmdao.api from scipy.integrate import solve_ivp

To see what's installed, run python -m pip list in the terminal. Each library has online documentation. Search "numpy linspace" and the official page is usually the first result.

4.3Raising errors on purpose

A wrong answer that looks fine is worse than a crash. raise ValueError("message") stops the program and says why. Make d04_crash.py:

{{code:d04_crash.py}} {{out:d04_crash.py|label=Output (an error, on purpose)}}

This traceback goes through two files. Read it from the bottom:

  1. The last line says what happened: ValueError: Altitude must not be negative, got -100.
  2. Just above, it shows where it was raised: atmos.py, line 11, inside density.
  3. Above that, it shows who called it: d04_crash.py, line 3.

So a traceback is a chain: the top is where your program started, and the bottom is where it broke. The fix is usually in your file (here: don't pass a negative altitude), even when the error is raised inside a library.

4.4Catching errors with try / except

Sometimes you expect an error and want to deal with it instead of crashing. Make d04_errors.py:

{{code:d04_errors.py}} {{out:d04_errors.py}}
try:
"Try to run the indented lines."
except ValueError as err:
"If a ValueError happens, don't crash. Run this block instead." as err stores the error so you can print its message.

Only catch errors you expect and know how to handle. Wrapping everything in try hides real bugs.

4.5Writing and reading files

Results should be saved to files so you can open them in Excel or plot them later. CSV ("comma-separated values") is a plain text table: one row per line, with columns separated by commas. Make d04_write_file.py:

{{code:d04_write_file.py}} {{out:d04_write_file.py}}
with open("atmosphere.csv", "w") as f:
Opens (or creates) the file for writing. "w" means write, and it replaces any existing file with that name. f is the name we give the open file. with makes sure the file is closed properly when the indented block ends.
f.write("altitude_m,…\n")
Writes text. \n is the special "new line" character. Without it, everything ends up on one line.
range(0, 30001, 5000)
0 to 30 000 in steps of 5000. The stop is 30001 so that 30000 is included.

The file it creates looks like this. Open it in Excel to see a table:

altitude_m,density_kg_m3,temperature_K 0,1.22500,288.15 5000,0.68025,255.65 10000,0.37775,223.15 ...

Reading it back, in d04_read_file.py:

{{code:d04_read_file.py}} {{out:d04_read_file.py}}
open("atmosphere.csv", "r")
"r" means read.
lines = f.readlines()
Reads the whole file into a list of strings, one per line.
for line in lines[1:]:
Skip line 0 (the header) with a slice.
line.strip().split(",")
strip() removes the invisible newline at the end, and split(",") cuts the text at each comma, giving a list of pieces.
float(parts[0])
The pieces are text. float() converts text like "5000" into the number 5000.0.

On Day 6, NumPy does all of this in one line. It's still worth knowing what happens underneath.

4.6Debugging: bugs that don't crash

The nastiest bugs give a wrong answer with no error. Make d04_buggy.py. The function says it wants kilometres:

{{code:d04_buggy.py}} {{out:d04_buggy.py}}

1.2207 kg/m³ at 30 km is clearly wrong, because it's almost sea-level density. How do you find the cause?

  1. Print the values in between. Add print("h_km =", h_km) inside the function. The values are fine. Then look at the formula: it divides kilometres by 8500, a number meant for metres. That's a units bug, the most common kind in engineering code.
  2. Use the VS Code debugger. Click just left of a line number to place a red dot (a breakpoint). Open the Run and Debug panel (the triangle-with-a-bug icon on the left, or Ctrl+Shift+D) and start "Python Debugger: Debug Python File". The program pauses at the red dot, and the Variables panel shows the value of every variable. Press F10 to run one line at a time, and F5 to continue to the next breakpoint.

The sanity-check habit

Before trusting any number, ask "is this roughly what I expected?" Air at 30 km should be about 3% of sea-level density. This habit will save you on every OpenMDAO and Dymos result.
