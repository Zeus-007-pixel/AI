10.1From running a model to optimizing it

So far you've run models once with values you chose. Optimizing means letting a driver choose the values. It runs the model over and over, each time adjusting the design variables to improve the objective while respecting the constraints. You add three kinds of declarations to the model:

CallDeclares
add_design_var('x', lower=…, upper=…)what the optimizer may change, and its bounds
add_objective('f')the one output to minimize
add_constraint('c', lower=…, upper=…, equals=…)outputs that must stay within limits

10.2The first optimization

Day 7's constrained paraboloid, now in OpenMDAO: minimize f subject to x + y ≥ 0. New file d10_optimize.py:

{{code:d10_optimize.py}} {{out:d10_optimize.py}}
p.model.add_subsystem('con', om.ExecComp('c = x + y'), promotes=['*'])
The constraint needs an output to watch, so this tiny component computes c = x + y. Its inputs x and y are promoted, so they're the same x and y the paraboloid uses.
p.model.set_input_defaults('x', 3.0)
x is now an input of two components with different starting values (0.0 in Paraboloid, 1.0 in the ExecComp). This says which starting value the shared input gets. See the error box below.
p.driver = om.ScipyOptimizeDriver()
Attach a driver to the problem. This one uses SciPy's optimizers from Day 7.
p.driver.options['optimizer'] = 'SLSQP'
Drivers have options too. Choose SLSQP. 'tol' sets how precisely to converge.
p.model.add_design_var('x', lower=-50.0, upper=50.0)
The optimizer may change x between −50 and 50.
p.model.add_objective('f')
Minimize f.
p.model.add_constraint('c', lower=0.0)
Keep c ≥ 0. Use upper= for ≤ and equals= for =.
result = p.run_driver()
Instead of run_model() (one run), run_driver() runs the optimization. SLSQP prints a short report.
result.success
True if the optimizer says it converged. Always check it.

x = 7, y = −7, f = −27: exactly SciPy's answer from Day 7.

Common error: ambiguous promoted inputs

Remove the two set_input_defaults lines and p.setup() or run_driver() stops with:

{{out:d10_ambiguous.py|tail=14|label=Error}}

Read it calmly: two components share the promoted input x but disagree on its starting value. The message even tells you the fix.

10.3Why declare_partials matters: a silent failure

Here is the same problem with the declare_partials line deleted from Paraboloid, in d10_no_partials.py:

self.add_output('f', val=0.0) # declare_partials line deliberately missing! {{out:d10_no_partials.py}}

It says Success: True, but the answer is wrong (f = −14.75 instead of −27). Without declared partials, OpenMDAO assumes f doesn't depend on x or y at all, so the optimizer thinks every direction is flat and stops. OpenMDAO did warn you, in the DerivativesWarning and DriverWarning lines: "objective(s) ['f'] do not depend on any design variables". Two lessons:

  1. Every component needs declare_partials (or the alternatives on Day 11).
  2. Read warnings. They are often the only clue to a wrong answer.

10.4An engineering optimization: the slowest level flight

Question: how slowly can our glider (500 kg, 10 m² wing) fly at sea level while lift still equals its weight, if the angle of attack must stay below 12°? This uses the FlightCondition group you saved in flight_components.py on Day 9. New file d10_slowest.py:

{{code:d10_slowest.py}} {{out:d10_slowest.py}}
from flight_components import FlightCondition
Reuse your Group from your own module (Day 4).
om.ExecComp('dL = L - m * g', …)
Excess lift. The constraint dL ≥ 0 means "lift is at least the weight".
add_design_var('v', lower=5.0, upper=300.0, units='m/s')
Two design variables, v and alpha. You can give bounds in any units: here alpha's bounds are in degrees although the component works in radians.
add_objective('v', ref=10.0)
Minimize speed. ref is scaling: "a typical value is about 10". The optimizer sees v/10, so all numbers it handles are around 1.
add_constraint('dL', lower=0.0, ref=1000.0)
Lift ≥ weight, scaled by a typical 1000 N.
p.set_val(…) after setup
The flight conditions and the starting guess for the design variables.

The answer is 30.92 m/s at exactly 12°. The angle sits on its upper bound: the optimizer pushed it as far as it was allowed, because more angle means more lift, so you can fly slower. Hand check: v = √(2W / (ρ·S·CL)) with CL = 4 × 0.2094 = 0.838 gives 30.9 m/s. ✓

Why scaling (ref) matters

Optimizers struggle when one number is 30 000 and another is 0.2, because a step that's tiny for one is huge for the other. Setting ref to a typical size of each design variable, objective and constraint makes them all roughly 1 in the optimizer's eyes. When an optimization misbehaves, scaling is the first thing to check.

10.5Maximizing

Two equivalent ways to maximize an output: add_objective('LD', scaler=-1.0), or a negative ref such as add_objective('x', ref=-1e4). Both flip the sign so the minimizer climbs instead of descends. Exercise 2 uses scaler, and Dymos on Day 15 uses a negative ref.

10.6Recording the optimizer's progress

A recorder saves the values at every iteration, so you can plot how the optimizer got there. New file d10_recorder.py:

{{code:d10_recorder.py}} {{out:d10_recorder.py}} {{img:history.png|The objective falls from 2782 to −27.33 in a few iterations}}
p.driver.add_recorder(om.SqliteRecorder('cases.sql'))
Attach a recorder to the driver. It writes a database file called cases.sql.
om.CaseReader(p.get_outputs_dir() / 'cases.sql')
Opens the recording. OpenMDAO saves it inside the …_out folder. p.get_outputs_dir() gives that folder, and / joins a folder and a file name into a full path.
reader.get_cases('driver')
A list with one entry ("case") per iteration.
case.get_val('f')[0]
The objective's value in that iteration.

10.7When an optimization fails: a checklist

  1. result.success is False, or the message says something like "Iteration limit reached" or "Positive directional derivative for linesearch". Go through the list below.
  2. Derivatives: does every component declare partials? Read every DerivativesWarning.
  3. Scaling: give ref values so everything the optimizer sees is around 1.
  4. Starting guess: start somewhere sensible, not at zero speed or zero density.
  5. Bounds: are they physically sensible? Is the answer sitting on a bound you didn't expect?
  6. Is the problem possible? Constraints that contradict each other can't be met.
  7. More iterations: p.driver.options['maxiter'] = 500.

  4. Think it through. In 10.4, why does the speed get lower as the angle-of-attack bound gets higher? What would happen with no upper bound on alpha in this model, and why is that unrealistic?

    Show answer

    Lift = q·S·CL, and CL grows with alpha in our model, so more alpha lets smaller q (lower speed) produce the same lift. With no bound, alpha would keep growing and the speed keep falling. Real wings stall (CL stops growing) at around 12–15°, but our straight-line CL = 4α doesn't know that. The model's limits must be enforced by bounds or constraints.
