1.1What programming is

A program is a list of instructions that a computer carries out one after another, exactly as written. It doesn't guess what you meant. If you write something slightly wrong, it either stops with an error message or quietly does the wrong thing.

Python is a language for writing those instructions. It reads almost like English, it's free, and engineers use it everywhere because of its libraries: ready-made code that other people wrote and shared. You'll use these libraries:

  • NumPy: fast math on lists of numbers
  • Matplotlib: plots
  • SciPy: simulations and simple optimizers
  • OpenMDAO: building and optimizing engineering models (NASA made it)
  • Dymos: trajectory optimization, built on OpenMDAO

A Python program is a plain text file whose name ends in .py. You write it in an editor (we use VS Code) and run it with Python.

1.4Comments

Anything after a # on a line is a comment. Python ignores it completely. Comments are notes for humans, including future you. Use them to say what a number means or why a line exists.

1.5Variables: named boxes for values

A variable is a name that holds a value. Make a new file d01_variables.py:

mass = 1000.0
Creates a variable called mass and stores 1000.0 in it. The = sign means "store the value on the right under the name on the left". It is not "equals" from maths, and it always works right-to-left.
g = 9.81
Same idea: a variable g holding 9.81.
weight = mass * g
Python first works out the right side: it looks up mass (1000.0) and g (9.81) and multiplies them (* means multiply). Then it stores the answer, 9810.0, in a new variable weight.
print(weight)
Prints the value stored in weight. There are no quotes, because we want the variable's value, not the word "weight".
print("The weight is", weight, "newtons")
You can give print several things separated by commas. It prints them in order with a space between each.

Rules for names: use letters, digits and underscores (_). A name can't start with a digit and can't contain spaces. Capitals matter: Mass and mass are two different names. Pick names that say what the value is: wing_area is better than x.

2.7while loops and your first simulation

A while loop keeps repeating as long as a condition is True. That's exactly what a simulation needs: "keep stepping time forward while the ball is still in the air."

The idea is called Euler's method, and it's the heart of every flight simulation. Over a small time step dt:

  • new height = old height + vertical speed × dt
  • new speed = old speed + acceleration × dt

The numbers that describe the ball at one instant (height and speed) are called its state. How fast they change (speed and acceleration) are its rates. Remember those two words: OpenMDAO and Dymos use them too. New file d02_while.py:

First 5 lines
Gravity, plus the starting state (height 0, upward speed 30 m/s), the clock (t = 0) and the time step (0.01 s).
while h >= 0:
Check the condition. If the height is still 0 or more, run the indented block, then come back and check again. Stop when it becomes False.
h = h + v * dt
Move the ball by speed × time step.
v = v - g * dt
Gravity reduces the upward speed by g × time step.
t = t + dt
Advance the clock.

The simulation gives 6.13 s and the exact answer is 6.12 s. The small difference comes from the finite time step. Make dt 10 times smaller and the answer gets closer, but the loop runs 10 times more often.

Infinite loops

If the condition never becomes False (for example you forgot to update h), the loop runs forever. Click in the terminal and press Ctrl+C to stop it.

3.1Why functions?

You've already used functions others wrote: print, len, math.sqrt. Today you write your own. A function is a named, reusable recipe: you give it inputs, it does its work, and it hands back an answer. Functions let you:

  • write a calculation once and use it many times
  • give a piece of logic a clear name, like density(h)
  • test one piece at a time

OpenMDAO components, Dymos ODEs and SciPy optimizers are all built from functions, so this is a key day.

3.2Defining and calling a function

New file d03_function.py:

def density(h):
def means "define a function". density is the name you choose. h inside the brackets is a parameter, a placeholder name for the input the function will receive. The line ends with a colon.
"""Return air density…"""
A docstring: a description in triple quotes on the first line inside the function. It's optional but good practice. VS Code shows it when you hover over the function name.
rho = 1.225 * math.exp(-h / 8500.0)
The function's work, indented. h holds whatever value was passed in.
return rho
return sends the answer back to whoever called the function, and ends the function right there.
print(density(0))
Calling the function. Python sets h = 0, runs the indented lines, and density(0) is replaced by the returned value, 1.225, which is printed.
rho_cruise = density(10000)
You can store the returned value in a variable and use it later.

Defining a function does not run it. The lines under def only run when the function is called. A function must be defined (higher up in the file) before you call it.

Common confusion: return vs print

print shows a value on the screen, and that's all. return hands the value back so your program can keep calculating with it. A function that prints but doesn't return gives back None, Python's word for "nothing". If you get TypeError: unsupported operand type(s) … 'NoneType', a function you called probably forgot to return.

8.1What OpenMDAO is, in plain words

OpenMDAO is NASA's framework for building engineering models from blocks and optimizing them. ("MDAO" means multidisciplinary design, analysis and optimization.) SciPy can optimize one function. OpenMDAO lets you build a big model from many small pieces, such as atmosphere, aerodynamics, propulsion and trajectory. Why scaling (ref) matters

Optimizers struggle when one number is 30 000 and another is 0.2, because a step that's tiny for one is huge for the other. Setting ref to a typical size of each design variable, objective and constraint makes them all roughly 1 in the optimizer's eyes. When an optimization misbehaves, scaling is the first thing to check.

10.7When an optimization fails: a checklist

  1. result.success is False, or the message says something like "Iteration limit reached" or "Positive directional derivative for linesearch". Go through the list below.
  2. Derivatives: does every component declare partials? Read every DerivativesWarning.
  3. Scaling: give ref values so everything the optimizer sees is around 1.
  4. Starting guess: start somewhere sensible, not at zero speed or zero density.
  5. Bounds: are they physically sensible? Is the answer sitting on a bound you didn't expect?
  6. Is the problem possible? Constraints that contradict each other can't be met.
  7. More iterations: p.driver.options['maxiter'] = 500.

11.1What a derivative is, in plain words

A derivative is a slope: how much an output changes when you nudge an input a tiny bit. If q = ½ρv² and you raise v by 1 m/s, q goes up by about ρv pascals. That ρv is the derivative of q with respect to v.

When an output depends on several inputs, a partial derivative is the slope with respect to one input while the others are held fixed. It's written ∂q/∂v (said "partial q, partial v"). In OpenMDAO code it's written partials['q', 'v'], and the two names are called of (the output) and wrt ("with respect to", the input).

Why optimizers need them: SLSQP stands on the current design and asks "which way is downhill, and how steep?" The partial derivatives answer that. OpenMDAO collects every component's partials and combines them, using the chain rule, into the total derivatives of the objective and constraints with respect to the design variables. Good derivatives mean fast, reliable optimization. Wrong derivatives mean failure, or a wrong answer.

11.2Three ways to get derivatives

MethodHow it worksAccuracySpeed
Finite difference method='fd'Nudge the input by a small step h, rerun, and compare: (f(x+h) − f(x)) / h.approximateslow
Complex step method='cs'A clever trick with imaginary numbers that avoids the rounding problem of FD.exact to computer precisionslow
Analytic (you write them)You differentiate the formulas by hand and code the results in compute_partials.exactfastest

Here's why FD is only approximate. New file d11_fd_error.py compares both methods on sin(x), whose true slope is cos(x):

FD has a dilemma. A big step is inaccurate because the curve bends within the step. A tiny step also goes wrong, because subtracting two nearly equal numbers loses digits to rounding (h = 1e-12 is worse than 1e-8). Complex step has no subtraction, so it just gets better as h shrinks. (1j is Python's imaginary unit. You never need to do complex maths yourself; OpenMDAO does it for you.)

Making code "complex-safe" for method='cs'

Complex step sends complex numbers through your compute. Most NumPy math handles them fine. Avoid things that throw away the imaginary part: abs() and np.abs(), float(...), if tests on input values, and math. functions. If cs gives strange derivatives, look for these.

11.5Which method should you use?

  • Just getting started, or the formulas are long: method='cs'. It's accurate with no effort. Make sure the code is complex-safe.
  • The component runs a black box such as a simulation, a table lookup or another program: method='fd'. That's the only option (Day 14).
  • Speed matters, or the model is big (Dymos problems with many nodes): analytic, checked with check_partials.

12.1Why vectorize?

So far each input held one number. Dymos needs your physics at many points in time at once: these are the nodes. Instead of running the component 60 times, you give every input and output a length of num_nodes, and NumPy computes all of them in one go (Day 6). Three changes turn a component into a vectorized one:

  1. an option num_nodes (often shortened to nn)
  2. arrays of length nn as starting values, such as val=np.ones(nn)
  3. derivatives declared as diagonal (12.2)

With 5 points, the derivatives of the 5 values of q with respect to the 5 values of v form a 5×5 table (a Jacobian). But q at point 3 only depends on v at point 3, so only the diagonal is non-zero:

v[0] v[1] v[2] v[3] v[4] q[0] [ ■ . . . . ] ■ = ρ·v at that point q[1] [ . ■ . . . ] . = always zero q[2] [ . . ■ . . ] q[3] [ . . . ■ . ] rows = [0,1,2,3,4] q[4] [ . . . . ■ ] cols = [0,1,2,3,4]

rows and cols list the positions of the non-zero entries: (0,0), (1,1), and so on. With 100 nodes that's 100 numbers instead of 10 000. This sparsity is what makes Dymos fast.

13.1Explicit vs implicit

Every component so far was explicit: output = formula(inputs). Some questions can't be written that way. "Which angle of attack makes lift exactly equal to weight?" is a condition the answer must satisfy, not a formula that produces it.

An implicit component describes its output with a residual, a quantity that must become zero when the output is right:

R(α) = L(α) − W = 0

A solver then searches for the α that makes R zero. It's like the optimizer's search, but finding a zero instead of a minimum.

13.2An ImplicitComponent and Newton's method

This uses FlightCondition from flight_components.py (Day 9). New file d13_implicit.py:

Inherit from ImplicitComponent instead of ExplicitComponent.
self.add_output('alpha', val=0.05, units='rad')
The unknown is an output of this component. val=0.05 is the solver's starting guess.
def apply_nonlinear(self, inputs, outputs, residuals):
Instead of compute, an implicit component provides this method. It doesn't calculate the output; it says how far from correct the current output is.
residuals['alpha'] = inputs['L'] - inputs['W']
The residual belonging to output alpha. It's zero exactly when lift equals weight.
The loop in the model
trim outputs alpha → aero uses it to compute L → trim needs L. That's a feedback loop, so running each block once in order can't solve it.
model.nonlinear_solver = om.NewtonSolver(solve_subsystems=True, maxiter=20, iprint=2)
Newton's method: guess α, measure the residual, use its derivative to jump to a better guess, and repeat until the residual is zero. maxiter limits the attempts, and iprint=2 prints each iteration. solve_subsystems=True makes Newton run the ordinary components first at each step, so L is up to date.
model.linear_solver = om.DirectSolver()
Newton needs to solve a small linear-algebra problem at each step. DirectSolver does that exactly.

The printout NL: Newton 0 ; 1842.5 1 means: at iteration 0 the residual is 1842.5 N. After one step it's 0 and it has converged. (One step is enough because L is a straight-line function of α here.)

Common error: "Singular entry found"

With solve_subsystems=False, the same model fails with RuntimeError: Singular entry found in <model> … for column associated with state/residual 'alpha'. Newton looked at the derivatives before the explicit components had run, when q was still at its starting value of 0. With q = 0, changing α seems to change nothing, so Newton can't decide which way to move. "Singular" means "some unknown seems to have no effect". Check that everything has been computed and that no starting value is zero where it matters.

14.3The wall you just hit

We forced one constant angle for the whole flight. A real pilot changes it continuously. So what's the best α at every moment? You could make α a list of, say, 100 values (one per 10 seconds) as 100 design variables. But then:

  • each FD derivative needs 100 extra simulations per optimizer iteration, which is very slow
  • adaptive solver steps and the landing event make the range slightly jumpy, so the FD derivatives get noisy and the optimizer struggles
  • adding constraints on the path, such as "q must stay below some limit at every moment", gets awkward

Finding a whole history of controls is called optimal control, and it needs a different approach. That approach is Dymos, tomorrow.

15.1The idea: draw the whole trajectory, then fix it

The capstone simulated forward in time and then adjusted α. Dymos turns this around. It uses a method called collocation:

  1. Split the flight time into segments and place a few points, called nodes, in each.
  2. Let the optimizer guess the state and the control at every node, all at once, as if drawing the whole trajectory freehand.
  3. At every node, Dymos runs your ODE component (vectorized over all nodes, Day 12) to get the rates the physics demands. It compares them with the slope of the drawn curve. The mismatch is called a defect.
  4. The defects become equality constraints (they must be 0). The optimizer adjusts the drawing until the physics is satisfied everywhere and the objective is as good as possible.
h │ o──o──o o = node: the optimizer's guess of the state there │ \ │ o──o at every node: slope of the drawn curve │ \ vs. rate computed by your ODE │ o──o difference = "defect" → must become 0 └──────────────────────── t

There's no simulation inside the optimization loop, the derivatives are exact and sparse (Days 11 and 12), and the control can take a different value at every node. That's what makes it fast and reliable for problems like your HGV.

15.3Reading the answer like an engineer

  • Range: 60.35 km, against 58.89 km for the best constant α on Day 14. Letting α vary over time buys about 1.5 km.
  • For most of the flight α sits at about 6.4°, the best-L/D angle you found on Days 6 and 10. Dymos rediscovered it on its own.
  • At the start, α is low: the glider trades its extra speed for distance before settling into the efficient glide.
  • At the end, α rises sharply: a final flare that turns the remaining speed into a little extra distance just before touching down.

Physics you can explain is the best evidence an optimization is right. Always look for it.

15.4Good to know before you go further

Control bounds at segment ends

With the Radau transcription, the control's lower/upper bounds are enforced where the control is a design variable. The value at the very end of each segment is extrapolated and can slip past the bound. While writing this course, a heavier glider showed α = 19.2° at the final node despite upper=15. The fix is a path constraint on the control, which checks every node: phase.add_path_constraint('alpha', upper=15.0, units='deg').

  • Check simulate=True. In the HTML report the simulated curves should lie on top of the optimized points. If they drift apart, use more segments.
  • Scaling and guesses matter even more than on Day 10. Give every state a ref, and guess a trajectory that's at least roughly physical.
  • Bigger problems (your 6-state HGV) are much happier with the IPOPT optimizer than SLSQP. It comes with pyoptsparse, which is easiest to install with conda (conda install -c conda-forge pyoptsparse). Then use p.driver = om.pyOptSparseDriver(optimizer='IPOPT').

15.5From this glider to your HGV

  1. Swap the ODE. Use your HGV_ODE, with 6 states (r, θ, φ, v, γ, ψ) and 2 controls (α, σ). Add one add_state per state and one add_control per control. Replace declare_partials('*', '*', method='cs') with declare_coloring(wrt='*', method='cs') (Day 12).
  2. Real atmosphere. Dymos ships a US 1976 standard atmosphere component: from dymos.models.atmosphere import USatm1976Comp. Put it in a Group with your ODE (Day 9), or use np.interp on a table (Day 6).
  3. Real aerodynamics. Compute L and D from ρ, v, S and CL/CD tables in α and Mach, so α finally matters.
  4. Limits as path constraints: heat rate (the Sutton–Graves formula from Day 5), dynamic pressure and load factor (Day 12), all as ODE outputs.
  5. The footprint. Solve the same problem several times with different objectives: maximize final θ (downrange), minimize it, and maximize ±φ (crossrange). Each solution becomes the initial guess for the next.
  6. Study the official example. Dymos includes a Space Shuttle reentry problem with the same kind of physics, in dymos/examples/shuttle_reentry in your installed package, and in the online Dymos documentation.
